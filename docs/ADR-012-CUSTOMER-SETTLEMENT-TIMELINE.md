# ADR-012: Customer settlement as linked event tracks

## Decision

External receipts are immutable payment evidence, not sales. The settlement model records independent customer-account events in integer KES minor units and links them through reversible allocations. A payment may be allocated to several customer debit events; an invoice may be settled by many credit events, but only for the same stable customer and currency.

```text
Commercial:  order ── invoice ── credit note
Fulfilment:       pick ── dispatch ── return
Money:             cash / M-Pesa / bank ── refund
Allocations:       payment ────────────────> invoice
Audit:              reviewer ── reversal history
Derived top layer:  customer balance, event status, next collection/refund action
```

The tracks intentionally do not collapse into one mutable “sale paid” record. The top layer is computed: a debit is `open`, `part-paid`, or `settled` from active allocation totals; unused credits remain available customer credit. Corrections retain history: credit notes are credit events linked to their originating invoice, while refunds are debit events that consume available credit through allocations.

## Boundaries

The customer registry API and Settings UI exist for authenticated roles. A separate authenticated bootstrap can copy valid server-stored `poultryFarmProfile.buyers` records into stable customers and retain a distinct legacy link for every canonical record plus duplicate occurrence; it never rewrites the profile JSON, merges names or phones, creates a pooled Walk-in customer, or backfills historical transactions. New sales can select an active stable customer, but the server revalidates that ID and derives the stored name/terms/status snapshot before persistence; Walk-in remains transaction-local COD. A newly created named-customer sale is an immutable posted invoice debit and posts its existing general-ledger receivable/revenue pair in the same SQLite unit; it creates no payment event or allocation, and its terms never prove payment. Invalid legacy records yield bounded index/code review issues while valid records are imported atomically. Reviewed M-Pesa imports and manual cash/bank receipts create unallocated payment credits. Authenticated staff may explicitly allocate already-posted same-customer KES credit evidence to debit evidence; allocations never create or edit events, sales, invoices, or GL entries, and reversal retains history without deletion. The settlement read returns exact integer-minor positions or `reconciliation_required` with null totals when evidence is unsafe or inconsistent. A super-admin or admin may issue one posted commercial credit note against its explicit posted invoice: it records a bounded reason code, posts Dr Sales Returns and Allowances (4050) / Cr Accounts Receivable (1200), and automatically allocates only that invoice’s exact remaining deficit. Any remainder stays customer credit. This is the sole automatic allocation; there is no matching engine, cash/bank/M-Pesa refund route, or payment-reversal route. A manual receipt must name an active stable customer; it creates only a payment credit plus one linked exact ledger pair (cash Dr 1000 or bank Dr 1020, both Cr 1200), never a sale or invoice. M-Pesa is deliberately excluded from the manual route and remains reviewed Payment Inbox evidence. `contact_phone` is registry PII exposed only to authenticated registry readers; it is never copied into payment imports or logs. `payment_import_id` is a nullable trace link for a reviewed M-Pesa payment event and is unique when present. Refunds are recorded only through a compound operation that creates the refund debit and its exact credit allocations atomically. Standalone posted payment reversals are intentionally deferred: a later compound operation must release original allocations and cap cumulative reversal. Full SMS text and secrets are not columns in this domain.

Customers are stable opaque identities, not deduplicated names or phone fragments. The registry has no pooled “Walk-in Customer”: anonymous COD sales remain transaction-local. Any credit, payment, refund, or balance requires a named stable customer selected or created explicitly.

Allocations execute inside a dedicated SQLite `BEGIN IMMEDIATE` connection, so concurrent writers cannot over-allocate and unrelated shared-connection operations cannot become part of the allocation transaction.

Batch 14D clarification: the earlier statement that no refund route exists is superseded. A super-admin or admin may explicitly create a source-funded refund for a named customer. It records a separate posted refund debit, exact allocations from identified available payment or credit-note credit, and Dr Accounts Receivable / Cr the selected cash, M-Pesa, or bank account. The operation records its bounded refund reason separately from the commercial credit-note `reason_code`; the refund event itself leaves that credit-note-only field null. A payment-method difference requires durable acknowledgement. There is still no refund automation, payment reversal, or matching engine.

Batch 15A adds a narrowly read-only reconciliation-suggestions endpoint for authorized staff. It ranks deterministic, same-customer KES payment/credit-note capacity against invoice deficits only after the settlement snapshot and active-allocation provenance are coherent. Suggestions are advisory candidates, never allocations: the endpoint performs no financial writes, makes no identity inference from names or phones, and returns reconciliation-required/null totals instead of candidates when evidence is unsafe or corrupt.

Batch 16A adds the authorized read-only Customer Accounts timeline UI. It renders the existing settlement snapshot as independent Commercial, Money, and Allocation tracks, together with the derived exact current position. Any unavailable settlement or suggestion read remains explicitly `Unavailable / reconciliation required`; suggestions remain explanatory review cues only, not a matching engine or automatic action.

Batch 16B adds a separate, authorized manual-receipt form for an active selected stable customer. It only calls the existing cash/bank receipt endpoint and records unallocated customer credit; it does not apply an invoice payment or create an allocation, sale, credit note, refund, or automatic match. Inactive customer history remains readable but cannot receive a new receipt from this form.

Batch 16C adds one explicit, staff-confirmed customer-credit-to-invoice allocation form. It is enabled only from a current exact settlement snapshot for an active named customer, uses one selected recorded payment/credit note and one selected open invoice, and changes only allocation evidence and the derived remaining positions. Suggestions are advisory only; they never submit an allocation. The form creates no money, sale, customer event, or general-ledger posting.

Batch 16D adds one explicit reversal form for an existing active credit-to-invoice allocation. It uses the existing idempotent reversal route with an empty request body, retains the allocation as reversed history, and changes no events, sales, money, or general-ledger entries. An inactive customer's exact historical evidence may be corrected; no new receipt or allocation may be created for that inactive customer.

Batch 16E adds a separate admin-only commercial credit-note form. It selects one coherent posted invoice from the current exact customer snapshot, previews its prior-note allowance and linked-invoice split, and calls only the existing credit-note route. The form never creates a receipt, refund, sale, payment reversal, free-form ledger entry, or allocation action of its own; the existing server service remains responsible for its bounded linked-invoice allocation and exact Dr 4050 / Cr 1200 posting. Inactive customer history remains eligible for this explicit commercial correction where the server accepts it.

Batch 16F adds a separate admin-only outgoing-refund form. It explicitly selects one or more available posted payment or credit-note credits from a current exact customer snapshot, requires their exact total to match the outgoing amount, and calls only the existing source-funded refund route. It is not a credit note or payment reversal. The form shows any payment-method difference for acknowledgement, records no client-side accounting logic, and uses the service's exact Dr Accounts Receivable / Cr selected tender posting. Inactive customer history remains eligible for this explicit correction where the server accepts it.
